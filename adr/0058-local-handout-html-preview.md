# ADR-0058 — Local HTML preview of a handout and its matching PDF

- **Status:** Accepted 2026-09-12
- **Date:** 2026-09-12
- **Deciders:** operator (+ assistant)
- **Migrated under ADR-0061: 2026-11-01** (source revision `12572a0`; the amendment history is in
  git).

## Context

The operator wants documents to be easier to read and check before delivery, with a PDF download at
the bottom. The handout renderer already converts one Markdown buffer into HTML before producing a
PDF, and the shared stylesheet already has screen and print treatments. A separate HTML authoring
format or PDF converter would add another document to reconcile when the objective is less work.

## Decision

The existing renderer accepts an optional `--preview-html <new-file>.html` for draft and final
renders. It uses the same converted body, styled for the screen with the **Tabularium design
system**: a browser-only `preview.css` that mirrors the design-system tokens and fonts (Lora,
Alegreya Sans, IBM Plex Mono; OFL) from the website implementation, inlined so the saved copy stays
self-contained. The PDF is rendered exactly as it would be without the option, from the ink-lean
handout house style (ADR-0032) — the preview never feeds the PDF, and a real-render test asserts
identical PDF bytes with and without it. After the PDF passes build-QA, a standalone HTML copy
embeds that exact PDF as its download, so moving or later editing a neighboring file cannot silently
change what the button retrieves. The copy needs no server, JavaScript, remote asset or
browser-print step. It carries a draft label when generated with `--draft`; neither variant asserts
that this saved copy remains the latest document.

Markdown remains the source. Review and correct it before the ordinary fact-check and sealing
sequence. This feature introduces no editor, verification shortcut, additional attested output kind,
or persistent site. The HTML is a disposable view, not evidence and not an extra sealed-unit
artifact.

Each preview is a new private file, never an overwrite. Its parent directory must already exist and
must be outside `med/handouts/`, whose units reject HTML. A preview sourced from a patient directory
must remain in that same person's record area (for example `med/analysis/previews/`), including
after resolving destination links. External patient-shaped sources must use their own checkout's
renderer; the preview command does not guess another checkout's record boundary. Synthetic draft
fixtures outside the patient tree remain portable. Nothing generated by this feature is tracked or
published.

The browser view supports prose, tables, lists and explicit web/email links. Embedded media, active
markup, arbitrary inline styles and relative links are refused when preview mode is requested,
before rendering. A narrowly matched table-cell alignment style preserves the existing Markdown
table extension's output. An explicit prose/table/link attribute set also excludes browser editing
and browser-only visibility features, which could otherwise let the screen and embedded PDF disagree
without any JavaScript. A content policy blocks scripts and automatic network loads. This is the
small text-document feature needed now; supporting media or editing belongs in a later decision with
a concrete use case.

## Alternatives considered

- **Browser printing:** would introduce a second PDF engine and bypass the existing PDF build-QA and
  byte binding. The button downloads the generated PDF instead.
- **An editable HTML master:** would require a save path back to the document plus re-verification
  after changes. Keeping two editable copies would recreate the drift the sealed unit prevents.
- **A local application/server:** unnecessary for reading a generated copy and saving an existing
  PDF. Direct browser editing and one-click regeneration are deferred.
- **Adding HTML to every sealed unit:** would change the attestation schema, lifecycle and
  historical units for an optional reading convenience. A disposable view outside the sealed lane
  suffices.

## Consequences

Proofreading gets a readable screen view in the Tabularium design system, with a usable PDF
download. The file is larger because it contains fonts and a PDF (the design-system fonts add about
280 KB before encoding), but has no companion-file or service dependency. Screen and paper now
differ in look as well as layout — brand typography on screen, the ink-lean house style on paper —
while the text is the same; PDF pagination still needs the existing visual inspection. The design
tokens are a mirrored copy of the website's, so a design-system change is mirrored into
`preview.css` rather than edited locally. Verified in a Chromium browser (the Claude desktop app's):
the design-system fonts load from the file itself with no network request, and a real click on the
button saved the PDF under its own name, byte-identical to the rendered file.

No preview is emitted when PDF build-QA fails or the renderer takes the TXT fallback. The PDF is the
primary artifact: it is promoted (and attested for a final render) before the optional HTML copy is
published. A late filesystem failure while publishing HTML returns a clear failure explaining that
the PDF remains intact and an existing sealed unit must not be re-sealed. Default render/seal calls
remain unchanged when the option is absent.

Verification lives in the existing `tools.handout_attest.test_attest` suite: private/no-overwrite
publication, source-person location, inert markup, design-system stylesheet with every font inlined,
embedded PDF bytes, identical PDF with and without the option, and real pinned-runtime draft/final
round-trips with failed-render and missing-factcheck controls. The unit suite already runs from
`checks/selftest.sh`; the actual render tests skip explicitly when the pinned environment is absent.
